# Phase 3 — refined acceptance criteria (PROPOSED, owner review needed)

`product/stories.json` holds LD-012…LD-017 with templated criteria (`DRAFT_NEEDS_REFINEMENT`), and the matching
`qa/test-cases.json` entries (QA-0089…QA-0136) are generic scenarios. This file proposes concrete, testable criteria
for Workstream B (architecture/CONTRACTS.md §1, §5) and maps each QA case to an executable check as the slices land.
Every decision the owner has not confirmed is marked **ASSUMPTION**; changing one changes the tests named next to it.
Status values follow `PHASE-1-ACCEPTANCE.md`: `AUTOMATED` (test exists and was run by the developer), `PLANNED`
(story not delivered yet), `BLOCKED` (reason given), `N/A` (reviewer to confirm). Developer runs are not independent
QA: every case stays `NOT_RUN` in `qa/test-cases.json` until QA executes it.

## Common rules (all Phase 3 stories)

1. **Security** (CONTRACTS §3). Every endpoint declares its permission with `@PreAuthorize`; no session → `401`,
   missing permission → `403`, both `application/problem+json`, and the request changes nothing. Unsafe requests need
   the CSRF token. The acting user comes only from `CurrentActor#require()`.
2. **Recording security events** for rejected access (story template, third criterion) belongs to Workstream A's
   `AuditLog` (LD-011). Phase 3 code does not write security events itself: **BLOCKED** on LD-011 for the "records
   relevant security events" half; the rejection half is automated per story.
3. **Errors** (CONTRACTS §4): bean validation → `400` with `errors[{field, code}]` and no echoed values; unknown id →
   `404`; duplicate or stale version → `409`; domain rule → `422` with `rule`. A malformed id in the path (not a UUID)
   is treated as an unknown id → `404`. Unreadable JSON (including an unknown enum value in a body, or a date that is
   not ISO `yyyy-MM-dd`) → `400` without a field list.
4. **Text input** is trimmed before validation and storage; a value that is empty after trimming counts as missing
   (`NotBlank` for required fields, stored as `null` for optional ones). Length limits count characters after trimming.
5. **Auditing columns**: every Phase 3 table row has `created_at`, `created_by`, and editable rows `updated_at`,
   `updated_by` and `version` (optimistic locking). Actor columns are `uuid not null` without a foreign key to users.
6. **Timeline**: every successful write to a case or its parties appends exactly one `case_event` in the same
   transaction; a failed write appends none.

## LD-012 Create legal case

| Field | Type | Rule |
|-------|------|------|
| `referenceNo` | text | Optional on create. When omitted the server generates `LD-YYYY-NNNNN`, where `YYYY` is the creation year (UTC) and `NNNNN` a per-year counter starting at `00001` without gaps, padded to 5 digits (a 100 000th case gets 6 digits). When supplied: 1–40 characters, letters, digits and `/ . _ -`, starting with a letter or digit (`Pattern`); unique ignoring case (`409`); must not start with `LD-` followed by a digit, which is reserved for generated numbers (`422 REFERENCE_NO_RESERVED`). Not changeable after creation. **ASSUMPTION** (generated by default, user-supplied allowed for migrated files; year in UTC, not Cairo time). |
| `title` | text | Required (`NotBlank`), at most 200 characters (`Size`). |
| `caseType` | enum | Required (`NotNull`): `CIVIL`, `CRIMINAL`, `COMMERCIAL`, `LABOR`, `FAMILY`, `ADMINISTRATIVE`; anything else → `Pattern`. **ASSUMPTION** (list of types). |
| `subject` | text | Optional description of the dispute, at most 4000 characters (`Size`). |
| `openedOn` | date | Required (`NotNull`), not after today (`PastOrPresent`, server clock). **ASSUMPTION** (no lower bound). |
| `status` | enum | Not accepted on create; every new case starts `OPEN` (LD-017). |

Acceptance criteria:

1. `POST /api/v1/cases` with `CASE_CREATE` and valid input answers `201`, `Location: /api/v1/cases/{id}` and the stored
   case: `id`, `referenceNo`, `title`, `caseType`, `subject`, `openedOn`, `status: OPEN`, `version: 0`, `createdAt`,
   `createdBy`, `updatedAt`, `updatedBy` (the acting user's id).
2. The creation appends a timeline event `CASE_CREATED` whose summary contains the reference number, with the acting
   user and the time.
3. Invalid input answers `400` listing every failing field with its constraint code, and stores no case and no event.
4. A supplied reference number already used by another case (ignoring case) answers `409`; two concurrent creations
   with the same reference number produce exactly one case. Concurrent creations without a reference number get
   distinct consecutive numbers.
5. `GET /api/v1/cases/{id}` with `CASE_VIEW` returns the same representation; an unknown or malformed id → `404`.
6. Without a session → `401`, without `CASE_CREATE` (create) or `CASE_VIEW` (read) → `403`; nothing is stored.
7. The database enforces the same rules when the application is bypassed: required columns, lengths, allowed
   `case_type` and `status` values, non-blank title, unique reference number ignoring case.
8. **`CaseLookup` port for Workstream C** (CONTRACTS §5): `find(UUID)` returns
   `Optional<CaseSummary(id, referenceNo, title, status)>` (empty for an unknown id);
   `recordEvent(caseId, type, summary)` appends a timeline event in the caller's transaction. `type` must match
   `[A-Z][A-Z0-9_]{0,63}` and `summary` be 1–500 characters, otherwise `IllegalArgumentException`; an unknown case →
   `NotFoundException`. The actor is the signed-in user (`CurrentActor#require()`), so it must be called within a
   request. **ASSUMPTION** (C calls it only during an authenticated request).

## LD-013 Edit and validate case

1. `PUT /api/v1/cases/{id}` with `CASE_EDIT` and `{ title, caseType, subject, openedOn, version }` applies the same
   field rules as LD-012 plus `version` required (`NotNull`), answers `200` with the stored case, `version` increased by
   one, `updatedAt`/`updatedBy` set to the acting user. `referenceNo` and `status` are not editable here.
2. A `version` that is not the current one answers `409` and changes nothing (optimistic locking).
3. The update appends `CASE_UPDATED` listing the changed field names; a request that changes nothing answers `200`,
   keeps the version and appends no event. **ASSUMPTION** (no-op updates are not recorded).
4. A case in `CLOSED` or `ARCHIVED` status cannot be edited: `422 CASE_READ_ONLY`. **ASSUMPTION**.
5. Invalid input → `400` with field codes; unknown case → `404`; no session → `401`; without `CASE_EDIT` → `403`.
6. The UI edit form shows the current values, field errors next to the fields in the chosen language, and a clear
   message on `409` asking to reload.

## LD-014 Case details and timeline

1. `GET /api/v1/cases/{id}` (LD-012) is the details view; the UI (`/cases/{id}`) shows all case fields, the
   parties (LD-016), the status action (LD-017) and the timeline. An address under `/cases/` that is not a UUID shows
   the not-found page. A 403 shows the shared access-denied page.
2. `GET /api/v1/cases/{id}/timeline` with `CASE_VIEW` answers a `PageResponse` of `{ id, type, summary, occurredAt,
   actorId }`, newest first (ties by id), with the shared paging rules. Unknown case → `404`.
3. Event types written by Phase 3: `CASE_CREATED`, `CASE_UPDATED`, `CASE_STATUS_CHANGED`, `PARTY_ADDED`,
   `PARTY_REMOVED`. Other modules add their own types through `CaseLookup#recordEvent` (e.g. C's proceedings).
4. Timeline events are append-only: there is no API to change or delete them. **ASSUMPTION** (events are never
   deleted; a deleted case keeps no timeline, case deletion is out of Phase 3 scope).

## LD-015 Case list search and filtering

1. `GET /api/v1/cases` with `CASE_VIEW` answers a `PageResponse` of case summaries
   (`id, referenceNo, title, caseType, status, openedOn, updatedAt`).
2. Parameters, all optional and combined with AND:
   - `q`: at most 100 characters; case-insensitive substring of the reference number or the title.
     **ASSUMPTION** (party names join the search with LD-016).
   - `status`: one or more statuses (repeat the parameter); `caseType`: one or more types.
   - `openedFrom`, `openedTo`: inclusive `yyyy-MM-dd` bounds on `openedOn`.
   - `page` (≥ 0, default 0), `size` (default 20, values above 100 become 100, below 1 → `400`).
   - `sort=<field>,<asc|desc>` with field in `referenceNo`, `title`, `openedOn`, `status`, `createdAt`, `updatedAt`;
     default `createdAt,desc`; ties broken by `id`.
3. An unknown status or type, a malformed date, an unknown sort field or a negative page → `400` naming the parameter
   (`typeMismatch`, `Pattern`, `Min`, `Size`). `openedFrom` after `openedTo` → `422 DATE_RANGE_INVALID`.
4. No session → `401`; without `CASE_VIEW` → `403`.
5. The UI list offers the search box, status and type filters, the paging controls, an empty-state message, and
   keeps the filters in the URL so that a reload shows the same page.

## LD-016 Legal parties and case relationships

| Field | Rule |
|-------|------|
| `kind` | Required: `PERSON` or `ORGANIZATION`. |
| `name` | Required, at most 200 characters. |
| `nationalId` | Optional, persons only: exactly 14 digits (Egyptian national number); unique among parties (`409`). **ASSUMPTION**. |
| `registrationNo` | Optional, organisations only: commercial registration number, at most 50 characters. **ASSUMPTION**. |
| `phone` | Optional, at most 30 characters of digits, spaces and `+ - ( )`. |
| `email` | Optional, a valid address of at most 254 characters (`Email`). |
| `address` | Optional, at most 500 characters. |

1. `POST /api/v1/parties` (`PARTY_MANAGE`) creates a party (`201` + `Location`); `PUT /api/v1/parties/{id}`
   (`PARTY_MANAGE`, with `version`) edits it; `GET /api/v1/parties?q=` and `GET /api/v1/parties/{id}` (`CASE_VIEW`)
   search and read parties. A `nationalId` on an organisation or a `registrationNo` on a person →
   `422 PARTY_KIND_MISMATCH`.
2. `POST /api/v1/cases/{id}/parties` with `{ partyId, role }` (`PARTY_MANAGE`) links a party to a case with role
   `CLIENT`, `OPPONENT` or `OTHER` (**ASSUMPTION**: these three roles), answering `201`; the same party twice on one
   case → `409`. `DELETE /api/v1/cases/{id}/parties/{partyId}` (`PARTY_MANAGE`) unlinks it (`204`).
   `GET /api/v1/cases/{id}/parties` (`CASE_VIEW`) lists the linked parties with their roles.
3. Linking appends `PARTY_ADDED`, unlinking `PARTY_REMOVED`, both naming the party and the role.
4. Parties of an `ARCHIVED` case cannot change: `422 CASE_READ_ONLY`. **ASSUMPTION**.
5. Validation `400`, unknown case or party `404`, `401`/`403` as in the common rules.

## LD-017 Case lifecycle status

Statuses: `OPEN` (registered), `ACTIVE` (being pursued), `SUSPENDED` (on hold, e.g. a stay of proceedings),
`CLOSED` (concluded), `ARCHIVED` (closed and filed away, read-only). Allowed transitions (**ASSUMPTION**):

| From | To |
|------|----|
| `OPEN` | `ACTIVE`, `CLOSED` |
| `ACTIVE` | `SUSPENDED`, `CLOSED` |
| `SUSPENDED` | `ACTIVE`, `CLOSED` |
| `CLOSED` | `ACTIVE` (reopen), `ARCHIVED` |
| `ARCHIVED` | none |

1. `POST /api/v1/cases/{id}/status` with `{ status, reason, version }` and `CASE_STATUS_CHANGE` applies an allowed
   transition, answers `200` with the case, increases the version and appends `CASE_STATUS_CHANGED` with the old and
   new status and the reason.
2. `reason` is optional, at most 500 characters, and required when reopening (`CLOSED` → `ACTIVE`):
   `422 REASON_REQUIRED`. **ASSUMPTION**. The event summary is `<OLD> -> <NEW>: <reason>`, shortened with `…` to
   the 500-character summary limit.
3. A transition not in the table, including to the same status → `422 STATUS_TRANSITION_NOT_ALLOWED`; nothing changes.
4. Stale `version` → `409`; unknown status → `400`; no session → `401`; without `CASE_STATUS_CHANGE` → `403`
   (`LEGAL_STAFF` does not hold it by default, CONTRACTS §3).
