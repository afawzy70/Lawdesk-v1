## A. Authorization: technical ADMIN must not obtain legal authority (QA-R6-M0-001, -014; revised in Round 3)

### A.1 EXISTING facts (verified in the develop tree)
| Path | What it does today | Source |
|---|---|---|
| Principal build | `LawdeskUser.of(account)`: ADMIN role → **every** `Permission` value, and the account's own role rows are ignored; other accounts → known codes of their roles' `role_permission` rows | LawdeskUser.java:36-46 |
| Account load | `UserAccounts.account()` reads `user_role` and **all** `role_permission.permission` of those roles, unfiltered | UserAccounts.java:125-133 |
| Principal refresh | The principal is rebuilt from the database on **every request** (roles apply next request; disabled user signed out; `credentialVersion` revokes sessions) | ReloadingSecurityContextRepository.java:58-73 |
| Role create | `RoleAdministration.create`: any code that is a known `Permission` name may be attached to a new role (`known()`) | RoleAdministration.java:61-70, 97-109 |
| Role update | `update`: for the ADMIN role the permission set **must equal `KNOWN` = every enum value** (`ADMIN_ROLE_FIXED`); other roles accept any known code | RoleAdministration.java:73-95 |
| User roles | `UserAdministration.create/setRoles`: users cannot change their own roles (`requireNotSelf`); granting a role whose permissions include USER_MANAGE/ROLE_MANAGE needs ROLE_MANAGE; the last enabled ADMIN stays | UserAdministration.java:80-160, 177-205 |
| Storage | `role_permission(role_id, permission varchar, primary key(role_id, permission))` — **no constraint on the value**; `user_role(user_id, role_id)`; **no per-user permission table exists** | V100__LD-007_app_user.sql:41-50 |

Consequences: (1) adding a value to `Permission` gives it to every ADMIN; (2) with `adminInherited=false` alone, the ADMIN-role invariant `permissions == KNOWN` would *force* the sensitive code onto the ADMIN role row, and `role_permission` rows for sensitive codes would flow back into `account.permissions` through the loader; (3) an ADMIN with ROLE_MANAGE can create a role carrying a sensitive code and assign it to **another** user (self-assignment is refused, a colluding second ADMIN is not); (4) a direct SQL insert into `role_permission` is unconstrained. Case-level filtering cannot remove an authority already held; it is not claimed to solve this.

### A.2 Single authoritative model: sensitive authorities live only in `legal_authority_grant`
Rule: a **sensitive authority** (`Permission` values with `adminInherited=false` and `sensitive=true`: `POSTJ_APPROVE`, `APPEAL_SETTINGS_APPROVE`, `LEGAL_GATE_APPROVE`, `LEGAL_AUTHORITY_CUSTODIAN`, `COMPLAINT_VIEW`, `COMPLAINT_CREATE`, `COMPLAINT_EDIT`, `COMPLAINT_PREPARE_DECISION`, `COMPLAINT_APPROVE`) can be obtained **only** through an active `legal_authority_grant` row. It can never come from the enum, from `role_permission`, from a role, from direct user assignment, or from delegation (a delegation is evaluated at use and never loaded into the principal). Seven layers enforce it (each with a test):

| # | Layer | Exact change | Test |
|---|---|---|---|
| 1 | Enum | `Permission(adminInherited, sensitive)`; all existing values `(true,false)`; the nine above `(false,true)`; a unit test enumerates `Permission.values()` and fails when a value is unclassified or when `sensitive ⇒ adminInherited` | T-SEC-3 |
| 2 | Principal | `LawdeskUser.of`: `granted = {p : ADMIN ∧ p.adminInherited} ∪ {c ∈ account.permissions : known(c) ∧ ¬sensitive(c)} ∪ account.legalAuthorities`. The ADMIN branch no longer ignores the account's own role rows (union, so ADMIN+LEGAL_MANAGER loses nothing) | T-SEC-1, T-SEC-2, T-SEC-4 |
| 3 | Loader | `Account` gains `legalAuthorities`; `UserAccounts.account()` fills it from `legal_authority_grant` rows that are active **now** (not revoked, valid window) and **filters sensitive codes out of the `role_permission` query result** (a leftover sensitive row is ignored and reported, never granted) | T-SEC-11 |
| 4 | Role administration | `RoleAdministration.known()` rejects sensitive codes (`FieldErrorException("permissions","SensitivePermissionNotGrantableByRole")`) on create and update; the ADMIN-role invariant becomes `permissions == INHERITED` (the set with `adminInherited=true`), not `KNOWN`; existing technical administration (create/edit non-sensitive roles, assign roles, reset passwords, last-admin rule) is unchanged | T-SEC-12, T-SEC-13 |
| 5 | Database | table `sensitive_permission(code)` (inserted by the migration, insert-only) and a trigger on `role_permission` (INSERT/UPDATE) that raises `check_violation` for any code in it: direct SQL and the previous release are refused too. A startup/nightly integrity check reports any pre-existing sensitive row (there is none at M1: the migration asserts it) | T-SEC-14 |
| 6 | User assignment | no direct per-user permission table is introduced; `UserAdministration` needs no new path. The self-role rule (`requireNotSelf`) stays; even a colluding ADMIN pair cannot move a sensitive authority because roles cannot carry it | T-SEC-15 |
| 7 | Delegation | a delegation is valid only if the **delegator holds the same active grant at the moment of use**, the scope is a subset, the window is open, it has been approved by a custodian, it cannot be re-delegated, and it never appears in `account.legalAuthorities`; the checker is evaluated in `AuthorityScope.require` inside the transaction | T-SEC-7 |

Spring Security: endpoints keep `@PreAuthorize("hasAuthority('…')")`; sensitive actions additionally call `AuthorityScope.require(actor, authority, target)` (A.5) which re-reads grants/delegations **in the transaction**. Stale sessions: the principal refresh covers the next request; the in-transaction re-read covers requests already in flight; a revoked grant between page load and submit gives 403 and no write (T-SEC-6). ADMIN's normal technical capabilities are preserved: the inherited set equals today's set (T-SEC-2).

### A.3 `legal_authority_grant`, delegation and audit
`legal_authority_grant(id, grantee_id, authority, scope_type ALL|UNIT|CASE_TYPE, scope_ref, valid_from, valid_to, requested_by, approved_by, approved_at, basis NORMAL|BOOTSTRAP, bootstrap_id, revoked_at, revoked_by, revoke_reason, version)`; CHECK `requested_by <> approved_by`, `approved_by <> grantee_id`. A normal grant is approved by a holder of `LEGAL_AUTHORITY_CUSTODIAN` in scope. Revocation: custodian (or the bootstrap procedure, A.4) with a reason; effective on the next request and inside any transaction that re-reads. `legal_authority_delegation(id, delegator_id, delegate_id, authority, scope_type, scope_ref, valid_from, valid_to, reason, approved_by, revoked_at, …)`. Every grant, revocation and delegation writes an `audit_event` (actor, before/after) and approval records store `grant_id`/`delegation_id` (T-SEC-8).

### A.4 First-custodian bootstrap (does not depend on any existing custodian)
Owner decision D-09 supplies the authorization; nothing is created until the owner decides. Design (PROPOSED):
1. **Owner authorization (outside the system).** The owner issues a written authorization naming **two distinct nominees** (N1, N2 — different people, both enabled `app_user`s, neither the operator) and the authority to bootstrap. Its file is hashed (SHA-256) and the reference and hash are recorded.
2. **Ceremony by an operator** with a dedicated database role `lawdesk_bootstrap` (not the application role; the application role has no privilege on the bootstrap tables). The operator runs `deploy/qa/…`-style tooling (to be written in M1, not now): `bootstrap_custodian.py open --owner-auth-ref … --owner-auth-sha256 … --nominee N1 --nominee N2`. Allowed only while **no active custodian grant exists** (checked in the function) — so it can never be used to add a custodian next to existing ones, and it never needs a custodian to approve it.
3. **Each nominee proves control of their identity**: the operator hands out a one-time token (stored as a hash, expires in 24 h) over a channel other than the web app; the nominee signs in normally (so their principal is the real authenticated account) and calls `POST /api/v1/legal-authority/bootstrap/confirm` with the token. The endpoint needs only an authenticated session whose user id equals a nominee; it grants nothing by itself.
4. **Completion.** When both nominees confirmed, one transaction creates two `LEGAL_AUTHORITY_CUSTODIAN` grants with `basis = BOOTSTRAP`, **cross-approved** (N1's grant `approved_by = N2`, N2's `approved_by = N1`), scope ALL. Four identities are therefore recorded: owner authorization (reference+hash), operator, N1, N2.
5. **Immutable evidence.** `legal_authority_bootstrap_event` is insert-only (trigger refuses UPDATE/DELETE) and hash-chained (`sha256(prev_hash ‖ payload)`); each event records actor, time, nominees, owner-authorization reference/hash and token hash. An export is committed to the operations evidence folder and the owner compares the authorization hash.
6. **Rollback / revocation.** (a) Before completion: `abort` event, tokens void. (b) After completion: a custodian revokes normally; or the operator, **with a second owner authorization** (same recording), runs `revoke-bootstrap`, which revokes every BOOTSTRAP grant. The system is then fail-closed again (no custodian, no sensitive authority, every approval refused) and a new bootstrap needs a new owner authorization.
7. Limitations stated: a database superuser can forge rows; the control is detective (hash chain, owner-held authorization hash, audit export), not preventive, at that privilege level.
Tests: T-SEC-16 (bootstrap needs both nominees' confirmations; with one confirmation no grant; with an existing custodian the procedure refuses; wrong user cannot confirm; expired/reused token refused; evidence rows immutable; revoke-bootstrap fail-closed).

### A.5 Scope validation (`AuthorityScope.require`)
(1) an active grant or valid delegation of the authority exists for the actor now; (2) its scope covers the target (case type / owning unit / all, via the existing `case_in_scope` semantics; a complaint's owning unit); (3) the actor passes the target's visibility predicate (`case_visible` or `complaint_visible`); (4) maker≠checker for approvals. Any failure → 403/404 per the visibility rule, evaluated **before** validation, with no write.

`Permission` (flags, new values, `Codes` constants), `LawdeskUser.of`, `Account` (+`legalAuthorities`), `UserAccounts.account()` (filter + grants), `RoleAdministration` (`known`, ADMIN invariant), new `AuthorityScope`, `LegalAuthorityGrantService/Controller`, `BootstrapController` + operator script; migration: `sensitive_permission`, trigger on `role_permission`, `legal_authority_grant`, `legal_authority_delegation`, `legal_authority_bootstrap*`, startup integrity check. `UserAdministration` is unchanged.

## B. Complaint confidentiality and the referral security model (QA-R6-M0-002, -009; revised in Round 3)

### B.1 EXISTING facts (verified)
`legal_case.confidentiality` NORMAL|RESTRICTED (V600:34-35); `case_in_scope` returns false for RESTRICTED, so a restricted case is visible only to its primary/alternate member, its creator, holders of an active `case_grant`, and users with an open task on it (`case_visible`, V600:154-175, V720). `LEGAL_MANAGER` has scope ALL over non-restricted cases (V600:79-80).

### B.2 Rules
1. A complaint is confidential by itself: visible only through `complaint_visible(complaint, user)` = (`COMPLAINT_VIEW` grant **and** (responsible researcher OR explicit complaint access-list entry OR organisational scope of the owning unit)). ADMIN has no access by role (A).
2. **Complaint ↔ case relationship.** One authoritative table `complaint_case_link(complaint_id unique, case_id unique, created_in_xid)`; a complaint is *referred* exactly when a link row exists (invariant R-1, enforced by a deferred constraint trigger in both directions: status «محالة للمحكمة» ⇔ exactly one link). A constraint trigger on the link requires, at insert time, `legal_case.confidentiality = 'RESTRICTED'`, complaint status = REFERRED, the case has no other link. A linked case is called **complaint-linked**.
3. **Atomic inheritance and rollback.** Referral completion (B.4) is one transaction: lock complaint → insert the case RESTRICTED (`primary_member_id` = responsible researcher, `owning_unit_id` = the complaint's) → insert the transfer copies → insert the link → status change + history + audit. Any failure rolls back **everything**, including the idempotency record; a retry starts clean or returns the already-committed case (T-CONF-6, T-PC11-6).
4. **Transfer manifest.** What moves is fixed by ¶196 («الأطراف، الوقائع، المستندات»): all respondents as parties plus CITRA's own side, the incident summary and date, and the complaint copy with its supporting attachments. Items classed *complaint-only* (investigation memoranda, prosecution requests and their responses, internal notes) never move. An exclusion of an item that ¶196 would otherwise carry needs the checker's reason, recorded. The manifest is prepared by `COMPLAINT_PREPARE_DECISION` and approved by a different holder of `COMPLAINT_APPROVE` in scope; the **policy** that allows manifests at all is owner policy `P-MANIFEST` (D-20, below) — a checker's approval of one manifest is not the owner's approval of the policy.
5. **Owner-policy switches (not legal gates).** `owner_policy(code, version, owner_authorization_ref, owner_authorization_sha256, decided_by_identity, decided_at, status)`, insert-only, written only by the bootstrap-style operator procedure of A.4 (so no application user can switch it). `P-MANIFEST` (referral may transfer data into a restricted case) and `P-DECLASS` (a complaint-linked case may ever become NORMAL) are **OFF** until the owner decides D-20; they are distinct from the nine legal gates because they record an owner's policy, not CITRA Legal Affairs' legal approval. Nothing is approved by implication.

### B.4 Referral: completion is mandatory, automatic and atomic (QA-R6-M0-009; source ¶194-196)
Source requirement kept: **completing a referral creates exactly one linked case automatically** (¶196). Therefore a complaint is never marked «محالة للمحكمة» without its case.
* **Referral draft.** The prosecution's referral is first a *draft fact* (`complaint_referral_draft`: referral decision date, competent court, case number, charges/articles, plus the intake values below). While any mandatory value is missing the complaint **stays «قيد التحقيق بالنيابة»**, no case exists, no link, no status change, and the draft shows an explicit **list of missing fields**. PC-11 is *unmet* (not "passed") until completion.
* **Completion.** When every mandatory value is present **and** the manifest is approved **and** `P-MANIFEST` is active **and** D-25 is approved, one transaction performs B.2(3). Invariant R-1 (status ⇔ link) holds before and after every commit.
* **Minimum mandatory source data** (¶194): referral decision date, competent court, court case number, charges/articles. **Minimum transfer** (¶196): parties, facts, documents (B.2(4)).
* **Mandatory intake fields** (IntakeRequest.java:24-43, 56-69) and their lawful source — none is invented:

| Intake field | Source of the value | If unknown |
|---|---|---|
| firstInstance.courtId | referral competent court | draft stays incomplete |
| firstInstance.courtCaseNumber | referral court case number | incomplete |
| firstInstance.courtCaseYear, filingDate | entered by the preparer (not in ¶194) | incomplete |
| automatedNo, title, caseType, openedOn, financialImpact | entered or confirmed by the preparer; the form may *propose* (opened-on = referral date) but the stored value is the confirmed one, recorded in the approval | incomplete |
| authorityPosition | mapping of «مجني عليها / شاكية» to a case side — **D-25 (owner)** | incomplete; completion blocked until D-25 |
| primaryMemberId | the complaint's responsible researcher | incomplete |
| parties | all respondents, resolved through the existing party registry (duplicate warning → `confirmDistinct` only by explicit user choice) | incomplete until resolved |

* **Adapter.** A `ReferralCaseFactory` builds the existing intake command through the case-intake **service boundary**, compiling on develop and on develop+R5 (R5 adds optional fields only) (T-R5-1).
* **Idempotency/duplicates.** Unique `complaint_case_link(complaint_id)` and `(case_id)` plus an idempotency key on the completion request; a retry or concurrent completion returns the same case (T-PC11-2). No column is added to `legal_case`.
* **Consequences stated:** until D-25 and D-20 are approved, referral can only be a draft; PC-10, PC-11 and PC-12 stay unmet in any build.

Paths that widen who can see a case: `POST /cases/{id}/grants` (`CASE_GRANT_MANAGE`), the case assignment update (primary/alternate member, CaseRepository:160-175), tasks (visibility through an open task).
Guards (service **and** database):

Changes to RESTRICTED are always allowed |
| DB trigger on `legal_case` (`before update of confidentiality`) | refuses `RESTRICTED → NORMAL` for a case with a link row unless a `declassification_approval` row with `xid = txid_current()` exists; refuses inserting a link for a NORMAL case. ### C.3 Concurrency and transaction order
Global lock order for every R6 write that touches a judgment: **(1)** parent `proceeding` `for update` (the existing `lockedProceeding`) → **(2)** `judgment` → **(3)** `judgment_procedural` → **(4)** `judgment_litigant` rows ordered by `(kind, id)` (CITRA first) → **(5)** `judgment_party_deadline` ordered by `(litigant order, appeal_type)` → **(6)** inserts of filings, child proceeding, history. Finality and filing both begin at (1) and are serialized: a filing after finality → `JUDGMENT_FINAL`; finality after a filing → `APPEAL_FILED`; finality re-reads non-VOID filings, unresolved litigants, running deadlines **and child proceedings of the judged proceeding that have no mapped filing** after taking the locks. Different litigants filing concurrently both succeed in any order; the same litigant twice → one row (unique index) and the replay returns it. `version` guards single-row edits (409) but is not the serialization mechanism. Tests: T-DATA-4, T-DATA-5, T-DATA-6 (real connections, latch, PostgreSQL 18; 50 mixed operations without deadlock), **T-DATA-13** (three opposing litigants file concurrently with CITRA's filing: four rows, no lost update), **T-DATA-14** (two filings racing to map to the same child: refused without the joinder approval; with it exactly one mapping order wins deterministically).

### C.4 Several appeals from one judgment
Each filing is an independent row; each resolves its own litigant's deadline; the judicial status becomes «منظورة …» on the first filing and stays so; no filing overwrites another; the judgment can become final only when **every** litigant is resolved and CITRA's decision is recorded. Matrix 03 §3.1 states one status with several filings.

### C.5 Immutable calculation evidence (QA-R6-M0-015)
`deadline_calculation_evidence(id, deadline_id, seq, kind INITIAL\|RECALCULATION\|MANUAL_APPROVED, inputs jsonb, result_due_on, computed_by, computed_at, reason, approval_id, grant_id, sha256)`, **insert-only** (trigger refuses UPDATE/DELETE). `inputs` embeds everything needed to reproduce the result without reading mutable tables: start date and basis, setting id and version, applied days, count method, `counts_start_day`, `roll_forward`, closed weekdays, **the holiday list actually used** (date, label, source, row id, row status/version) and the legal reference. A later holiday or setting edit never alters stored evidence; a recalculation appends a new row (both complete versions remain) (T-DATA-11, T-PJ16-2, T-ST05-1).

## D. Legal activation gates (QA-R6-M0-006)

### D.1 Mechanism
`legal_approval(id, subject_type, subject_id, subject_version, scope, effective_from, effective_to, legal_reference, decision_document_ref, approver_id, grant_id, approved_at, status ACTIVE\|SUPERSEDED\|REVOKED)` — versioned, insert-only (revocation = a new row). `LegalGate.require(subject, scope, date)` is called in the **service layer** at every action that gives legal effect; there is no controller-only check. DB defence in depth: a trigger refuses `deadline_setting.status = 'ACTIVE'` unless an ACTIVE approval for that exact version exists, and refuses inserting an approval whose approver lacks an active grant or equals the setting's author (T-GATE-3, T-GATE-7).

### D.2 What is gated and what is not
**Fact capture is never blocked** (an appeal was filed; the opponent says it appealed; a date was served): it is recorded with `legal_basis_status = UNAPPROVED`. **Legal effect is gated**: computing or activating a due date (G-CALC: D-01..D-04), settings use (G-SETTING: D-01, D-16), opponent start rule (G-OPPONENT: D-05), finality (G-FINAL: D-07), manual override (G-OVERRIDE: D-13), grievance deadline (D-10 → G-CALC), manager recipients (G-ALERT: D-14, recipient policy approved), post-grievance path (G-GRIEVANCE: D-11), stage model beyond the ladder and any joinder of filings into one child proceeding (G-STAGE: D-08), reopening (G-REOPEN: D-24).

### D.4 "No persistent side effects" — exact negative test

Refusals are written to the application log only, not to domain tables or `audit_event`. (T-GATE-1)

### D.5 M1 is schema, history and draft only
M1 contains: tables, constraints, history/append-only triggers, draft capture of procedural status and fact records (judgment details, party start dates and basis, filings recorded as facts), UI to view/enter them. M1 **excludes**: any due-date computation, effective manual duration, finality, automatic next-stage creation, settings activation, alerts. See 04 §D.

## E. Settings overlap, precedence and boundaries (QA-R6-M0-008)
Scope of a setting: `(judgment_level, appeal_type, case_type or ALL, effective_from, effective_to)`, ranges **half-open** `[effective_from, effective_to)`; `effective_to` is the first day it no longer applies (NULL = open-ended); `effective_to > effective_from`. Two ACTIVE settings **conflict** iff same level, same appeal type, their date ranges intersect, and (same case type **or** either is ALL). Enforcement: a trigger on activation takes `pg_advisory_xact_lock(hash(level, appeal_type))` and runs the intersection query (so `ALL` vs a specific type is caught — plain equality exclusion would miss it); a `btree_gist` exclusion on `(level, appeal_type, case_type, daterange)` is kept as a backstop for identical scopes. Because overlaps are refused, **no precedence rule is needed**: at most one active setting matches a given level, appeal type, case type and date. Which date matches: the date the judgment is **registered** in LawDesk (consistent with ¶94 "new judgments only"), stored in the evidence — a legal question recorded in D-16. Adjacent ranges ([a,b) then [b,c)) are allowed (T-ST04-2); concurrent activations: one wins, the other gets 409 (T-ST04-4). Remains inactive until D-16 and D-01 are approved.

## F. Alert publication: one transaction, honest status, idempotency, visibility, retry (QA-R6-M0-013, Round 3)

### F.1 EXISTING facts (verified)
`NotificationPublisher.publish(...)` (notifications/NotificationPublisher.java:41-63) runs **in the caller's transaction**, builds `dedupe_key = type:recordRef[:token]:userId`, inserts into `notification` only if the user exists **and has not switched that type off** (`notification_preference.enabled = false`), `ON CONFLICT (dedupe_key) DO NOTHING`, and returns `true` only when a row was inserted. **`false` therefore means any of: duplicate, preference off, unknown user, null user** — the boolean cannot distinguish them.

### F.2 Transaction boundary and statuses (PROPOSED)
One database transaction **per (subject, subject_version, offset, recipient)** performs, in this order:
1. `insert into alert_history(…, status='PENDING') on conflict (natural key) do nothing returning id` — no row returned ⇒ already handled ⇒ stop (no second notification).
2. Publish through a new overload `publishWithOutcome(...)` (added in M3; the boolean API is unchanged for its callers) that returns `CREATED | DUPLICATE | PREFERENCE_OFF | RECIPIENT_UNAVAILABLE`.
3. `update alert_history set status = …, notification_id = …` from the outcome: `CREATED` (notification row exists; `notification_id` mandatory), `SUPPRESSED_PREFERENCE`, `SUPPRESSED_RECIPIENT`, `SUPPRESSED_RESOLVED` (party resolved before firing), `SUPPRESSED_POLICY` (manager policy off). `DUPLICATE` is impossible after step 1 unless a legacy notification with the same key exists; then `CREATED` is recorded with the existing `notification_id`.
Database invariants: `status = 'CREATED' ⇒ notification_id is not null` (CHECK); `notification_id` unique FK; unique natural key `(kind, subject_type, subject_id, subject_version, offset_days, recipient_id)`.
There is **no FAILED status in `alert_history`**: a failure rolls the whole transaction back, so nothing claims a delivery that did not happen; the next run retries. Failures are counted in `alert_job_run(id, started_at, finished_at, attempted, created, suppressed, failed, error_text)`, written in a **separate** (`REQUIRES_NEW`) transaction so the failure record survives the rollback. Two instances: the second's step 1 waits for the first's transaction and then conflicts and stops; a per-run advisory lock only avoids needless contention.

### F.3 Semantics
* **Disabled preference:** history `SUPPRESSED_PREFERENCE`, no notification; re-enabling does **not** back-fill older alerts (same rule as the manager policy). Whether urgent/expiry alerts may override a user's preference is an owner question recorded in D-15.
* **Recalculation** → new evidence `seq` = new `subject_version` → fresh alerts; earlier ones are not retracted. **Offset change** → only offsets not yet raised for that version; removing an offset retracts nothing.
* **Resolution** (appeal, approved non-appeal, confirmed no-appeal, non-grievance, grievance filed) → the job skips that subject and may record `SUPPRESSED_RESOLVED`.
* **Recipient visibility** is checked at creation (predicate of the record) and again when notifications are listed; a recipient whose access/scope/authority is revoked gets no new alert and cannot read old ones.
* **Manager policy:** DISABLED (default) → researcher only; enabling later does not back-fill; missing mapping → researcher only plus a data-quality notice to ADMIN users with no case details. Payloads carry references only.

### F.4 Fault-injection tests (all assert exact row counts in `alert_history`, `notification`, `alert_job_run`)
T-ALERT-5: exception after step 1 and before step 2 → no history, no notification; the next run creates both once. T-ALERT-6: exception after step 2 and before step 3, and a failure at commit → no history, no notification. T-ALERT-7: preference off → one `SUPPRESSED_PREFERENCE` row, zero notifications; re-enable → still zero; replay → unchanged. T-ALERT-8: connection killed mid-transaction → no orphan; two threads on one key → one `CREATED`; job run twice and restart → one notification per key; a pre-existing legacy notification with the same key → one history row pointing at it, no second notification. Plus T-ALERT-1…4 and T-AL06-2/3.

## G. Grievance and closure guard (QA-R6-M0-007)
`complaint_grievance(id, complaint_id, filed_on, status PENDING\|DISPOSED, disposition, disposed_on, …)`. Closure of a «محفوظة» complaint is allowed only if **no grievance is PENDING** and (a non-grievance decision is approved **or** the grievance deadline has elapsed with no grievance filed). A filed grievance therefore keeps the complaint open until a recorded disposition; the allowed dispositions and what follows (including referral) are D-11 (BLOCKED), so until approved the complaint stays PENDING and cannot be closed (T-PC09-2, T-PC14-2).

### I.2 Invariants (database triggers, evaluated for every writer except a superuser)
* **I-1 `judgment.final`.** For a linked judgment, `final` may change only if a `judgment_finality` row with `xid = txid_current()` exists (inserted by the finality transaction, itself guarded by G-FINAL and the approval record). Insert/update of an unlinked judgment is unchanged.
* **I-2 `judgment.appeal_deadline_id`.** For a linked judgment the value must equal the CITRA litigant's effective deadline (or be NULL when none) and may change only inside an R6 transaction.
* **I-3 `judgment_date`/`outcome`.** For a linked judgment with an effective party deadline, changes are refused (a recalculation path with evidence exists instead).
* **I-4 `deadline`.** For a linked deadline: INSERT with a linked judgment as source refused; UPDATE of any legal column (`starts_on`, `period_days`, `due_on`, `rule_id`, `calc_status`, `approved_by/at`, `status`, `completed_on`, `change_reason`, `source_*`, `action`) requires a `deadline_calculation_evidence` (or resolution) row with `xid = txid_current()`; `notes` and `owner_id` stay editable.
* **I-5 association.** `judgment_party_deadline.deadline_id` may be set only if the `deadline` is `calc_status='APPROVED'`, an evidence row with the same `xid` exists, and an **ACTIVE `legal_approval`** covers that evidence (setting version, scope, effective date); otherwise refused. Evidence insert itself is guarded by the same approval check.
* **I-6 finality precondition.** The `judgment_finality` insert requires: every litigant resolved, every party deadline resolved or elapsed, no non-VOID filing pending, **no child proceeding of the judged proceeding without a mapped non-VOID filing**, the approved condition set (D-07) and the maker-checker approval.
* **I-7 reconciliation** (startup and nightly, read-only): for every linked deadline `due_on` equals the latest evidence result; for every linked judgment `final` equals the finality state and the pointer equals I-2; any mismatch (possible only through a superuser or a bypassed trigger) raises an ADMIN notice **and blocks alerts and finality for that judgment** until reviewed.
"Effective" = a deadline with `calc_status='APPROVED'` backed by an ACTIVE approval.

### I.4 Previous-release compatibility and operational rollback
Triggers apply to the previous release too: on a linked record its legacy write fails with a database error (the safe outcome: refused, no side effect; the exact HTTP status the old release returns is not guaranteed and is not asserted). Unlinked judgments and deadlines work as before. This **removes** the earlier hazard that an old release could silently edit an extension-backed deadline (03 §1.3 revised). After an application rollback R6 screens and jobs stop, R6 data remain, and legacy operations on linked records fail closed until roll-forward. T-MIG-3 includes these refusals.
