## Decision gate

GitHub documents that self-hosted runner execution is free of Actions minutes. This makes a runner a *possible* answer to the confirmed hosted-compute quota, but it does not prove that GitHub will execute a self-hosted job while this account is blocked. The [PR #49 probe checks](https://github.com/afawzy70/Lawdesk-v1/pull/49/checks) show the current-head job pending under label `lawdesk-ci-poc-49`, while its hosted CI jobs failed before a step ran. A queued job is admission evidence, not execution evidence. A payment failure, spending stop, policy restriction, or account hold may have different effects. The only accepted GO evidence is the `Self-hosted scheduling probe` job executing on a temporary runner and appearing as a successful check on this PR. Until then, migration is NO-GO.

## Production design after a successful proof

- For the approved Contabo host, require a verified hardened, disposable container or stronger isolated runtime for each job. A long-lived host account cannot establish the required trust boundary by Unix permissions alone. If the host cannot enforce filesystem, network, kernel and resource boundaries without impacting shared services, do not run untrusted PR CI on it.
- Grant the CI environment no route to Contabo application services or deployment SSH, and no credentials for LawDesk or Matbakhy. Keep repository token permission at `contents: read` except the existing `develop-guard` read scopes. Avoid exposing the CI job to production/staging keys.
- Run one job per disposable container, wipe its writable layer afterward, bound CPU/memory/disk/concurrency, and apply image and runner updates. Avoid a host Docker socket. Docker-based PostgreSQL and stack smoke jobs require a separate independently isolated build environment with an ephemeral container daemon; defer them until that boundary is verified.
- Keep the existing job names and commands so historical check identity and dispatch guard stay valid. Migrate policy, frontend, backend, secret scan, and then `develop-guard` one at a time only after the probe succeeds. The guard needs its current read-only GitHub scopes and must still gate every push to `develop`.
- Automatic deployment also uses a GitHub-hosted runner today. Moving only CI would leave it blocked. The immediate safe path is to restore hosted billing for the existing deployment job. A self-hosted alternative would need a **separate, trusted** deployment execution path with workflow-level runner admission enforced outside an editable PR workflow, and the current forced-command SSH gate key delivered only to the approved `develop` deploy job. A repository label alone is not an access control: a PR can request that label. Unless that admission boundary is proven, deployment migration is NO-GO. Never put the deployment key on the general CI VM.
- A failed or skipped check is never reported as PASS. Existing branch protection is unavailable on this private repository's plan; the `develop-guard` is detection after a push, not server-side prevention. Preserve the owner merge procedure in `docs/delivery/DEVELOP-PROTECTION.md`.
