# إعدادات المواعيد القانونية — دليل المختصين

الأساس: ترحيلات `V680–V682`، ومتحكما `DeadlineController` و`DeadlineSettingsController`، وأدلة `docs/evidence/DOC-WP4/README.md`، والقرار D6 («لا احتساب قانوني آلي إلا بعد إدخال قواعد ومصادر وعطلات موثقة واعتماد المختص؛ لا اختراع مدد»).

## 1. القاعدة الأساسية: لا شيء مزروع

بعد الترحيلات تكون الجداول `deadline_rule` و`official_holiday` و`deadline_reminder_setting` **فارغة تمامًا**، ولا تحتوي الشيفرة ولا SQL على مدة ولا طريقة عدّ ولا يوم عطلة ولا عطلة رسمية ولا عدد أيام تذكير (يؤكد ذلك الاختبار `theApplicationShipsNoRuleNoHolidayAndNoReminderSetting`). النتيجة العملية:

| ما لم يُدخَل بعد | الأثر |
|-------------------|--------|
| قاعدة معتمدة | «اقتراح ميعاد» يردّ 422 برمز `NO_APPROVED_RULE`؛ يبقى تسجيل المواعيد **يدويًا** |
| عطلات رسمية معتمدة | الحساب لا يتخطى سوى أيام الأسبوع المغلقة التي تنص عليها القاعدة |
| أيام التذكير | **لا يُنشأ أي تنبيه «اقتراب ميعاد»**؛ ينشأ فقط تنبيه «تجاوز الميعاد» (لا يحتاج مدة) |

## 2. من يفعل ماذا

| الإجراء | الصلاحية | المسار |
|---------|-----------|--------|
| عرض القواعد والعطلات والتذكير | `DEADLINE_VIEW` | `GET /api/v1/deadline-rules`، `/official-holidays`، `/deadline-settings/reminders` |
| إنشاء/تعديل **مسودة** قاعدة أو عطلة | `DEADLINE_MANAGE` | `POST/PUT /api/v1/deadline-rules`، `/official-holidays` |
| **اعتماد** قاعدة أو عطلة، أو **سحبها من الاستعمال** | `DEADLINE_APPROVE` | `POST .../{id}/approve`، `.../{id}/retire` |
| ضبط أيام التذكير | `DEADLINE_APPROVE` | `PUT /api/v1/deadline-settings/reminders` |
| تشغيل التذكير يدويًا | `DEADLINE_APPROVE` | `POST /api/v1/deadlines/reminders/run` |

الشاشة: `/admin/deadlines` (عناوينها: «قواعد المواعيد القانونية» وتبويباتها «قواعد المواعيد» و«العطلات الرسمية» و«التنبيهات قبل الميعاد»). افتراضيًا يحمل الصلاحيات الثلاث ADMIN وLEGAL_MANAGER وSECTION_HEAD وLEGAL_STAFF؛ وDATA_ENTRY وREAD_ONLY `DEADLINE_VIEW` فقط. الاعتماد مسؤولية **المختصين القانونيين** الذين يحددهم المالك؛ أما المدد والمصادر فلا يقترحها النظام ولا الوثيقة.

## 3. إدخال قاعدة

من تبويب «قواعد المواعيد» أدخل **كل** الحقول التالية؛ لا قيمة افتراضية لأي منها:

| الحقل | القيد |
|-------|--------|
| `code` الرمز | أحرف/أرقام/`_.-` حتى 60، ويُفرد مع `effectiveFrom` |
| `label` الوصف | إلزامي حتى 300 حرف |
| `periodDays` المدة | من 1 إلى 3650 يومًا |
| `countMethod` طريقة العدّ | `CALENDAR` (أيام متتالية) أو `WORKING` (أيام عمل) |
| `countsStartDay` | هل يُحتسب يوم البدء نفسه |
| `rollForward` | هل ينتقل ميعاد يقع في يوم مغلق إلى أول يوم مفتوح (يفيد في العدّ `CALENDAR`) |
| `closedWeekdays` | أيام الأسبوع المغلقة بالأرقام 1 (الاثنين) … 7 (الأحد) وفق ISO؛ قد تكون فارغة؛ قاعدة `WORKING` تحتاج يومًا مفتوحًا واحدًا على الأقل |
| `legalSource` **المصدر القانوني** | إلزامي غير فارغ حتى 1000 حرف |
| `effectiveFrom` | تاريخ سريان القاعدة |

الحالات: `DRAFT` ← `APPROVED` ← `RETIRED`. الاعتماد يحفظ اسم المعتمِد وتاريخه، ولا يقبل النظام اعتماد قاعدة بغير مسودة. **القاعدة المعتمدة لا تُعدَّل** (`RULE_NOT_DRAFT`): لتغيير مدة أنشئ قاعدة جديدة بتاريخ سريان لاحق (يجوز تكرار الرمز بتاريخ سريان مختلف) واسحب القديمة. المسحوبة لا تُستعمل في اقتراح جديد، وما حُسب بها سابقًا يبقى مخزنًا بحسابه كاملًا.

## 4. إدخال العطلات الرسمية

تبويب «العطلات الرسمية»: `holidayOn` (التاريخ)، `label` (حتى 200)، و`legalSource` إلزامي (حتى 1000). تاريخ واحد لا يتكرر بين العطلات غير المسحوبة (`HOLIDAY_DATE_TAKEN`). مسودة ← اعتماد ← سحب بالطريقة نفسها؛ **المعتمدة وحدها** تدخل الحساب. إدخال عطلة أو سحبها لاحقًا لا يعيد كتابة اقتراحات سبق حسابها.

## 5. أيام التذكير قبل الميعاد

تبويب «التنبيهات قبل الميعاد»: قائمة أعداد أيام (مثل 7 و3 و1 — مثال توضيحي لا افتراض)، بحد أقصى عشر قيم لكل منها بين 0 و365. تُرتَّب وتُحفظ بصف واحد، ويُسجَّل التعديل في التدقيق (`DEADLINE_REMINDERS_SET`). بعد الضبط، يُنشئ التشغيل الساعي لكل ميعاد **معتمد ومفتوح** تنبيهًا داخليًا واحدًا عند بلوغ كل عدد أيام، للمسؤول عن الميعاد والعضو المختص بالقضية. المواعيد اليدوية أو المقترحة غير المعتمدة ليست رسمية فلا تنتج تنبيهات. لا إرسال خارج النظام (D11). عدد الأيام واحد لكل الأنواع، ولا نموذج لنوع الميعاد (طعن/تمييز/تظلم) إذ يصفه نص «الإجراء المطلوب» ومصدره.

## 6. كيف يُحسب الاقتراح

`POST /api/v1/cases/{caseId}/deadlines/propose` (يتطلب `DEADLINE_MANAGE` وحق تعديل القضية وقضية غير مؤرشفة) بالمدخلات: المصدر (`JUDGMENT` أو `HEARING` أو `PROCEEDING` أو `TASK` أو `TEXT` مع معرّف من القضية نفسها)، `ruleId`، `startsOn`، الإجراء المطلوب، المسؤول. الخطوات:
1. تُرفض القاعدة إن لم تكن موجودة ومعتمدة (`NO_APPROVED_RULE`)، أو إن كان `startsOn` قبل `effectiveFrom` (`RULE_NOT_EFFECTIVE`)، أو كانت قاعدة `WORKING` أيام أسبوعها كلها مغلقة (`RULE_NOT_COUNTABLE`).
2. **اليوم الأول المعدود** = يوم البدء إن كانت القاعدة تعدّه، وإلا اليوم التالي.
3. `CALENDAR`: ميعاد النهاية = اليوم الأول + المدة − 1؛ وإن وقع في يوم مغلق (أسبوع مغلق أو عطلة معتمدة) وكانت `rollForward` فينتقل إلى أول يوم مفتوح.
4. `WORKING`: تُعدّ أيام المدة المفتوحة فقط؛ تُتخطى الأيام المغلقة وعطلات معتمدة، وتُسجَّل كل واحدة.
5. النتيجة تُخزَّن بحالة **`PROPOSED`** مع الحساب الكامل (القاعدة ومصدرها القانوني، أول يوم معدود، كل يوم متخطى بنوعه، ونقطة الانتقال). ويظهر في لوحة «كيف حُسب التاريخ».

## 7. اعتماد ميعاد

`POST /api/v1/deadlines/{id}/approve` (`DEADLINE_APPROVE` **و**حق تعديل القضية؛ العضو المختص أو البديل أو حامل `CASE_EDIT_IN_SCOPE` في نطاقه). شروطه: أن يكون له تاريخ نهاية (`DEADLINE_NO_DUE_DATE` وإلا)، وألا يكون معتمدًا (`DEADLINE_ALREADY_APPROVED`)، وأن يطابق `version` الذي قرأه المعتمِد (409 عند التعارض). يُحفظ المعتمِد والوقت وتُسجَّل حادثة `DEADLINE_APPROVED` في القضية والتدقيق.
- **المقترح لا يُنجَز قبل اعتماده** (`DEADLINE_PROPOSAL_PENDING`).
- تعديل تواريخ ميعاد مقترح أو معتمد يدويًا **يعيده `MANUAL`** ويتطلب سببًا (`DEADLINE_CHANGE_REASON_REQUIRED`) واعتمادًا جديدًا، وينسى القاعدة.
- لا شيء يُنجَز أو يُفوَّت أو يُغلق أو يُعتمد آليًا؛ «متأخر» حالة مشتقة (مفتوح وتجاوز تاريخه).
- الجدول الزمني والتقويم يعرضان المواعيد اليدوية والمعتمدة، **لا المقترحة غير المعتمدة** في التقويم.

## 8. تسلسل عمل مقترح للمختصين

1. يجمع المختص المصدر القانوني لكل مدة يريد حسابها آليًا (المرجع نص نظامي أو لائحي، لا هذه الوثيقة).
2. يُدخل القاعدة مسودة بكل حقولها، ويراجعها زميل يحمل `DEADLINE_APPROVE`، ثم تُعتمد.
3. يُدخل العطلات الرسمية للسنة بمصدرها ويعتمدها.
4. يحدد المالك أيام التذكير فتُضبط من «التنبيهات قبل الميعاد».
5. يجرّب العضو اقتراح ميعاد على قضية حقيقية، ويقارن الحساب المعروض بما يعرفه، ثم يعتمد أو يعدّل يدويًا.

## 9. ما هو مؤكَّد وما لم يُجرَّب

- مؤكَّد باختبارات (39 اختبارًا في `com.lawdesk.deadlines`): الحساب بقواعد **اختبارية** تُنشأ داخل الاختبار وتُزال، والرفض 422، والاعتماد، والتذكير، والظهور في الجدول الزمني.
- رحلة UAT (`tools/journeys/wp4_journey.py`) تُدخل قاعدة وعطلة اصطناعيتين بتاريخ 2000/2001 وتسحبهما قبل أن تنتهي؛ سجّل التقرير نجاحها لـ«المواعيد اليدوية والقواعد المعتمدة»، لكن **السيناريو S14 كاملًا ينتظر إدخال المختصين قواعد وعطلات حقيقية**.
- غير مبني: `judgment.appeal_deadline_id` (بديله `deadline.source_type = JUDGMENT`)، وتذكير بحسب نوع الميعاد، وجعل مستند الإثبات إلزاميًا عند الإنجاز (اختياري حاليًا)، ومصدر تقويم لمواعيد التنفيذ.
