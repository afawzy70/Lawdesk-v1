## Security architecture verdict

**REJECTED (VERIFIED baseline + INFERRED impact).** The deployed backend is configured to use `lawdesk_app` ([compose:45–55](https://github.com/afawzy70/Lawdesk-v1/blob/18822a83bff8e2a38b83db4370674a9f69919d81/deploy/compose.yaml#L45-L55)); [app-role.sql:7–16](https://github.com/afawzy70/Lawdesk-v1/blob/18822a83bff8e2a38b83db4370674a9f69919d81/deploy/postgres/app-role.sql#L7-L16) creates the lawdesk schema with that owner on a fresh install. No separate Flyway user is configured in [application.yaml:7–24](https://github.com/afawzy70/Lawdesk-v1/blob/18822a83bff8e2a38b83db4370674a9f69919d81/backend/src/main/resources/application.yaml#L7-L24); [Spring Boot's Flyway documentation](https://docs.spring.io/spring-boot/how-to/data-initialization.html) says it uses the primary datasource by default. [PostgreSQL 18 privileges](https://www.postgresql.org/docs/18/ddl-priv.html) assign object ownership to the creating role and permit owners to modify their objects; [ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html) permits disabling user triggers. The proposed triggers, append-only flags and policy tables are therefore not a boundary against direct SQL with the application credential on this path. Actual UAT object ownership remains uninspected. This is not a hypothetical superuser exception: it is the configured runtime account. Technical ADMIN inheritance is addressed in the Java-level design, but the legal authority and confidentiality protections are not end-to-end.
