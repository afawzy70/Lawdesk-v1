# Independent side restore of a real V781 dump — source 18822a8

Executed 10 November 2026 using the application JAR built from exact source `18822a83bff8e2a38b83db4370674a9f69919d81`, PostgreSQL server/client 18.6, and a throwaway cluster bound to loopback under `/tmp/lawdesk-qa-188-oldbackup-20261110`. The tool was `tools/restore-drill/restore_old_backup.py` from that SHA with `--target 781 --scale 1`. It never connected to UAT. Full structured evidence: `restore-old-18822a8/drill-result.json`; uncommitted raw 118 MB dump stays in the QA scratch directory. The run took 278.9 s. QA separately hashed the dump on disk and confirmed its size and SHA-256 match the evidence record. The cluster exited and its `postmaster.pid` was removed.

This was a **real `pg_dump -Fc` file from a V781 database**, not a simulated SQL fragment. It held 300 synthetic cases, 600 documents, 1,200 versions (70,971,384 stored version bytes), 40 library judgments and linked/granted records. The tool recorded 21 checks, and QA inspected their individual `ok` fields: 21 true, 0 false.

- Direct `pg_restore --exit-on-error` failed at `CREATE TABLE library_judgment` because `library_normalize(text)` was not found within the old `library_trigrams` definition. Only 63/88 tables existed and the judgment table was absent. Continuing without `--exit-on-error` still returned code 1, reported 14 ignored errors and left the same table missing. Thus applying V800 to source code alone would not repair this old dump.
- The documented one-line `SET search_path TO 'lawdesk'` addition to the plain restore script succeeded (`psql` return 0, empty stderr). The restored database had 88/88 tables and all 40 synthetic library judgments. All stored file bytes matched their SHA-256/size columns; foreign keys (131), links and grants were checked. Four persona visibility counts matched the source: manager 267, head 173, staff 225, archivist 187.
- Starting the exact-source application applied 10 later migrations (V800 onward), validated the schema and exposed the API. The repaired restore and the independently migrated old source gave identical API fingerprints for the four personas, including case/document reads and downloaded file hashes. The post-migration database fingerprint had no differences for the compared rows, files, keys, links, versions, grants and structure. The only pre-migration structure digest difference was the intentional function search-path repair.

This independently verifies the **V781 synthetic dump recovery procedure** and the failure of a naïve restore. It does not prove that every historical pre-V800 production dump (different earlier schema, extensions, volume paths or corruption) will restore. No owner backup was supplied or used; an authorized representative old backup needs the same side-restore validation before an operational recovery claim. Do not restore over UAT. QA-RT-003 remains open for that broader historical-backup assurance, with its reproduced V781 subcase now passing.
