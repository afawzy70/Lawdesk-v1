# Shared contracts for parallel delivery of Phases 2, 3 and 4

Owner decision 2026-10-24: Phases 2, 3 and 4 are built concurrently. This file holds the rules that let three
workstreams change the code base at the same time without conflicting migrations, competing security models or a
duplicated case model. Changes to it go through a pull request reviewed by the integration owner (Claude, workstream
A). Tests pin the code parts down, as noted in each section.

## 1. Ownership

| Workstream | Stories | Backend packages | Frontend folders | Flyway versions |
|------------|---------|------------------|------------------|-----------------|
| A, Phase 2: security, users, audit | LD-007…LD-011 | `com.lawdesk.security`, `com.lawdesk.users`, `com.lawdesk.audit` | `src/features/auth`, `src/features/admin` | `V100`–`V199` |
| B, Phase 3: cases | LD-012…LD-017 | `com.lawdesk.cases` | `src/features/cases` | `V200`–`V299` |
| C, Phase 4: judicial lifecycle | LD-018…LD-023 | `com.lawdesk.courts`, `com.lawdesk.proceedings` | `src/features/courts`, `src/features/proceedings` | `V300`–`V399` |
| Shared (integration owner only) | — | `com.lawdesk.platform`, `com.lawdesk.api` | `src/api`, `src/layout`, `src/i18n/catalog.ts` | `V1`–`V99` |

A workstream edits only its own rows. When it needs a shared change, it asks for one with a small, separate pull
request against `develop`, and does not make the change on its feature branch.

## 2. Database migrations

- Each workstream numbers its migrations inside its own range, in the order it creates them:
  `V<n>__<story>_<what>.sql`, for example `V200__LD-012_legal_case.sql`.
- Flyway runs with `out-of-order: true`. A `V105` merged after a `V210` is still applied. Future versions stay
  ignored on rollback (`*:future`). `MigrationOrderingTest` covers both.
- Migrations are forward-only and never edited after merge. Fixes ship as new versions.
- **Cross-range references** point only to lower ranges, and only to tables that are already on `develop`.
- **Actor columns:** `created_by` / `updated_by` are `uuid not null` columns **without** a foreign key to the users
  table. That keeps B and C independent of A's migrations; audit columns record who acted, and the user is never
  deleted.
- **Identifiers** are `uuid` primary keys generated by the database (`default gen_random_uuid()`).
- **Optimistic locking:** editable aggregates carry `version bigint not null default 0`.
- **Timestamps** are `timestamptz` in UTC. Calendar dates are `date`.

## 3. Security (owned by A; B and C consume it)

- **Session.** Login is a browser session: the HttpOnly cookie `JSESSIONID`, `Secure` behind HTTPS and
  `SameSite=Lax`. No token is ever stored in `localStorage`.
- **CSRF.** The cookie `XSRF-TOKEN` is readable by the SPA, and the SPA echoes it in the `X-XSRF-TOKEN` header on
  every unsafe request. `src/api/http.ts` does this, and every API call goes through it.
- **Endpoints (A):**
  - `POST /api/v1/auth/login` with `{ "login": "<username or email>", "password": "…" }`.
  - `POST /api/v1/auth/logout`.
  - `GET /api/v1/me` returns `{ id, username, displayName, email, locale, roles[], permissions[] }`.
- **Authorities are permission codes.** `com.lawdesk.security.Permission` is the only list; the frontend mirrors it in
  `src/api/permissions.ts`, and a test keeps the two equal. Roles are database rows that group permissions.
- **Every protected endpoint** declares its permission with `@PreAuthorize(Permission.Codes.CASE_CREATE)`. Method
  security is on. Requests without a session get 401, requests with a missing permission get 403, and both are RFC 9457
  problems.
- **Acting user.** `com.lawdesk.security.CurrentActor#require()` returns the signed-in user as
  `ActorRef(UUID id, String username)`. The authenticated principal implements `ActorPrincipal`. Domain code uses
  `CurrentActor`; it never reads the `SecurityContext` itself.
- **Tests in B and C** authenticate with `com.lawdesk.security.TestActors.as(Permission...)`, a MockMvc request
  post-processor in the test sources. Because it builds the same principal type as real logins, tests written now keep
  working once A's login exists.
- **Audit (A).** Security events go through `com.lawdesk.audit.AuditLog`. Business history, such as the case timeline
  (LD-014), belongs to its own module.

### Default roles (seeded by A, editable through role administration, LD-009)

| Role | Permissions |
|------|-------------|
| `ADMIN` | all |
| `LEGAL_MANAGER` | every `CASE_*`, `PARTY_MANAGE`, every `COURT_*`, `PROCEEDING_*` and `JUDGMENT_*`, `USER_VIEW`, `AUDIT_VIEW` |
| `LEGAL_STAFF` | `CASE_VIEW`, `CASE_CREATE`, `CASE_EDIT`, `PARTY_MANAGE`, `COURT_VIEW`, `PROCEEDING_VIEW`, `PROCEEDING_MANAGE`, `JUDGMENT_VIEW` |

`CASE_DELETE`, `CASE_STATUS_CHANGE`, the management of courts and judgments, users, roles and audit are
manager/admin-only by default. The last active `ADMIN` can never be disabled, lose the role, or be removed (LD-009).

## 4. API conventions (`com.lawdesk.api`, shared)

- **Paths:** REST under `/api/v1`, with plural nouns: `/api/v1/cases`, `/api/v1/courts`,
  `/api/v1/cases/{caseId}/proceedings`.
- **JSON:** camelCase fields; ids as UUID strings; ISO-8601 `Instant`s and `LocalDate`s.
- **Errors** are `application/problem+json`. `ApiExceptionHandler` maps:

  | Situation | Status | Body |
  |-----------|--------|------|
  | bean validation failure | 400 | `errors: [{ field, code }]`, where `code` is the constraint name (`NotBlank`, `Size`…); no rejected values are echoed |
  | `NotFoundException` | 404 | — |
  | `ConflictException`, or an optimistic-lock failure | 409 | — |
  | `BusinessRuleException` | 422 | `rule: "<CODE>"` |

  Unexpected errors return a 500 without details.
- **Lists:** `?page=0&size=20&sort=<field>,<asc|desc>`, where `size` defaults to 20 and is capped at 100. The answer is
  `PageResponse { items[], page, size, totalItems, totalPages }`.
- **Writes** return the stored representation. Creations answer 201 with `Location`. Updates send `version` and get 409
  when it is stale.

## 5. Case model boundary (owned by B; C references it)

- **B owns** `legal_case`, `party`, `case_party` and `case_event` (the timeline), and the case status lifecycle (LD-017).
- **C owns:**
  - `court`, the reference data, with a `level` of `FIRST_INSTANCE`, `APPEAL` or `CASSATION`;
  - `proceeding` (`case_id` → `legal_case.id`, `stage`, `court_id`, the case number and year at the court, and
    `parent_proceeding_id` for an appeal or a cassation);
  - `judgment` and `special_decision`.
- **C never writes B's tables.** It reads cases only through `com.lawdesk.cases.CaseLookup` (`find(UUID)` returning
  `CaseSummary(id, referenceNo, title, status)`), which B delivers first.
- **Before B has merged**, C codes against that interface with a test double and adds the `legal_case` foreign key in
  its first migration that follows B's `V200`.
- **Proceedings do not appear in the case timeline automatically.** When a proceeding is recorded, C calls
  `CaseLookup#recordEvent(caseId, type, summary)` (B), so B owns the timeline table.

## 6. Frontend

- **Folders:** each workstream builds under its own `src/features/<area>`.
- **Navigation:** areas come from `src/layout/navigation.ts`. An item declares the permission it `requires` and a
  `status` of `ready` or `planned`. `visibleNav(permissions)` shows only ready items the user may open; planned items
  keep the "coming later" page. A workstream flips its own item to `ready` when its first screen works.
- **Messages** live per area in `src/i18n/messages/<area>.{en,ar}.ts`, which the core catalogs spread. Every area file
  already exists, so a workstream edits only its own two files. `catalog.test.ts` still checks that both languages
  have the same keys.
- **API calls** go through `src/api/http.ts`, which sends credentials, sets the CSRF header and turns problems into
  `ApiError`.

## 7. Delivery

- **Branches and PRs:** one `feature/LD-0xx-…` branch per story or slice, each a small PR against `develop` that names
  its story IDs. Every PR goes through RED, GREEN, REFACTOR, then CI.
- **QA:** the exact head SHA goes on the PR for QA (Codex, through GitHub).
- **Merging:** the integration owner merges after CI is green and no known critical defect remains, and every merge
  deploys to UAT automatically. Unfinished screens stay `planned` in navigation.
- **Story order:**
  - B delivers `CaseLookup` with LD-012.
  - C starts with LD-018, the court reference data, which needs no case data.
  - A delivers login (LD-007) first, because the screens of B and C need a signed-in user on UAT.
